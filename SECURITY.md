## Что сделано для безопасности в рамках фронтенда

- Сессия валидируется по белому списку `director | admin | dispatcher | engineer`.
  Битая/неизвестная сессия трактуется как отсутствие входа.
- Рабочему (`engineer`) в веб-панели доступен только `/scanner`; прямой
  переход на `/defects` и `/users` блокируется `RoleGuard` и показывает 403.
- Пункт «Сотрудники» скрыт для диспетчера, а прямой переход на `/users`
  дополнительно блокируется через `RoleGuard` и проверку внутри `Users`.
- Ключ доступа — 10 символов, генерируется через `crypto.getRandomValues`;
  в справочнике хранится только PBKDF2-SHA-256-хеш с индивидуальной солью.
- Ключ не показывается администратору и не попадает в таблицу или
  `sessionStorage`. В демо он сохраняется только в mock-outbox
  `promscan:mail-outbox:v1`, имитирующем почту сотрудника. Перевыпуск заменяет
  хеш: старый ключ перестаёт работать для новых входов.
- Поля формы валидируются: обязательное ФИО из двух слов, формат email,
  запрет дубликата email, роль ограничена правами создающего.
- Камера: поток останавливается при уходе со страницы, при сбросе и после
  снимка. Видео не записывается и никуда не отправляется.
- Загрузка фото: проверяется MIME-тип `image/*` и размер до 10 МБ,
  файл читается локально через `FileReader`, без сетевой отправки.
- Нет `dangerouslySetInnerHTML`, `eval`, динамического выполнения кода и
  вставки пользовательских строк как HTML. React экранирует вывод.
- Нет токенов и паролей в исходниках и `.env`. Публичные демо-ключи из README
  намеренно не являются секретами; в production их быть не должно.

## Важные ограничения (не production-готово)

### 1. Сессия в sessionStorage — не авторизация

`sessionStorage` можно изменить через DevTools, а PBKDF2-проверка выполняется
в браузере. Скрытие меню и `RoleGuard` — это UX/defense-in-depth, а не контроль
доступа.

**Для production:** роль должна приходить из подписанной серверной сессии
(JWT/HttpOnly cookie), проверяться на каждом API-запросе и в серверном
middleware. Клиент не должен быть источником истины о правах.

### 2. Ключи и хеши на клиенте

В демо справочник сотрудников с солями и хешами лежит в `localStorage`.
Открытые ключи в таблице не показываются, но хеши доступны браузеру и могут
быть скопированы. Кроме того, mock-outbox хранит текст письма с ключом —
это имитация почтового ящика сотрудника, а не production-хранилище.

**Для production:** генерировать ключ на сервере, хранить только Argon2id-хеш,
отправлять ключ письмом и никогда не возвращать его в API/UI. Не хранить
хеши и ключи в localStorage/JS-состоянии, добавить аудит-лог и отзыв сессий.

### 3. Демо-ключи опубликованы

Ключ директора `PSCDRT2345` и ключи сотрудников из README — публичные ключи
стенда. Они не являются секретами и не должны использоваться в production.

**Для production:** выдавать ключи только владельцу, не хранить их в
репозитории/README, добавить rate limiting, MFA для директора и блокировку
после неудачных попыток.

### 3.1. Активные сессии не отзываются при перевыпуске

Демо хранит сессию только в `sessionStorage` вкладки и не знает версию ключа.
После перевыпуска старый ключ не подходит для новых входов, но уже открытая
вкладка продолжает работать до закрытия.

**Для production:** хранить `session_version`, инвалидировать все сессии
пользователя при перевыпуске и проверять `/api/auth/me` при старте и фокусе.

### 4. Валидация только на клиенте

Проверки email, дубликатов, ключей и ролей выполняются в браузере. Их можно
обойти.

**Для production:** дубликаты email — уникальный индекс в БД; роль — проверка
на сервере; нормализация email; rate limiting на вход и создание сотрудников.

### 5. Камера и приватность

`getUserMedia` запускается при открытии `/scanner`, то есть браузер сразу
запрашивает разрешение. Поток останавливается на `unmount`, но в production
лучше добавить явную кнопку «Включить камеру» и индикатор записи.

**Для production:** HTTPS, заголовок `Permissions-Policy: camera=(self)`,
политика хранения снимков, согласие оператора, запрет записи без уведомления.

### 6. Загрузка файлов

Сейчас файл не покидает браузер. Если появится серверная загрузка, нельзя
доверять MIME-типу: нужна проверка сигнатуры, лимиты, антивирус, хранение вне
web-root и рандомные имена.

### 7. XSS / CSP

XSS-векторов в текущем коде не найдено: нет `dangerouslySetInnerHTML`,
пользовательские данные выводятся как текст. Для production рекомендуется
добавить CSP без `unsafe-inline`/`unsafe-eval`, `X-Content-Type-Options`,
`Referrer-Policy` и `Permissions-Policy`.

### 8. CSRF / API

В mock-режиме API-запросов нет, поэтому CSRF неприменим. В real-режиме
`src/lib/api.ts` уже использует `fetch`, но без cookie/CSRF-контракта.
При добавлении бэкенда:
HttpOnly + Secure + SameSite cookies, CSRF-токены для state-changing запросов,
CORS с явным allowlist. Ключ передавать только по HTTPS.

## Рекомендованный чек-лист перед production

- [ ] Перенести аутентификацию и RBAC на сервер.
- [ ] Заменить демо-ключи на серверную выдачу и проверку Argon2id.
- [ ] Убрать соли/хеши и сессию из клиентского состояния.
- [ ] Добавить rate limiting входа, перевыпуска ключей и писем.
- [ ] Реализовать почтовый провайдер и одноразовый код подтверждения.
- [ ] Отзывать активные сессии при перевыпуске ключа и смене роли.
- [ ] Добавить серверную валидацию, уникальные индексы и rate limiting.
- [ ] Настроить CSP, Permissions-Policy, HTTPS и security-заголовки.
- [ ] Добавить аудит действий (создание сотрудника, смена роли, доступ к /users).
- [ ] Подключить Dependabot/`npm audit` в CI.
- [ ] Добавить e2e-тесты реальной авторизации и прямых переходов по URL.
