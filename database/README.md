# База данных насосов и показаний датчиков PromScan

Этот каталог содержит PostgreSQL-артефакты и инструкции к ним. Backend и frontend в эту ветку не входят. Ветка `database` создана независимо (orphan) и не содержит историю или файлы приложения.

Существующие frontend-файлы и mock-данные приложения не удалялись и не изменялись: они находятся в другой ветке и в другом worktree. В этой ветке только материалы БД.

## Состав

- `sql/001_schema.sql` — схема `promscan`, каталог оборудования, характеристики, узлы, документы и история обслуживания.
- `sql/002_seed_pumps.sql` — идемпотентное добавление четырёх агрегатов AMS PCP60S12/3 и данных, переписанных из паспортов.
- `sql/003_measurements_schema.sql` — схема показаний: датчики, каналы измерений, связи датчик–канал, партии импорта, измерения, диагнозы источника и пороги.
- `sql/004_seed_measurement_catalog.sql` — каталог каналов, метаданные двух demo-источников и пороги из описаний. Синтетические строки показаний не загружаются.
- `sql/005_measurement_views.sql` — представления для будущих API-запросов: статус партий, измерения по оборудованию и последнее значение по каналу.
- `sql/employees/001_schema.sql` — сотрудники и последнее состояние приглашения; база `promscan_employees`.
- `sql/tasks/001_schema.sql` — акты осмотра/задачи и контролируемый жизненный цикл; база `promscan_tasks`.
- `sql/credentials/001_schema.sql` — хеши ключей доступа, серверные сессии и одноразовые коды; база `promscan_credentials`.

PDF-паспорта и Excel-файлы в Git не добавлены. В таблицах сохраняются имена и исходные пути на Яндекс.Диске; это метаданные, а не URL для скачивания. В рабочей системе файлы следует хранить в согласованном объектном хранилище или документном сервисе.

## Отдельные БД сотрудников, задач и учётных данных

Новые наборы физически разделены на три PostgreSQL database, а не только на схемы одного database. Все используют схему `promscan`, но размещаются независимо:

| PostgreSQL database | SQL | Назначение |
|---|---|---|
| `promscan_employees` | `sql/employees/001_schema.sql` | Справочник сотрудников и текущее состояние приглашения |
| `promscan_tasks` | `sql/tasks/001_schema.sql` | `Report` из API-контракта: осмотр, назначение и ремонт |
| `promscan_credentials` | `sql/credentials/001_schema.sql` | Argon2id-хеши access key, хеши сессий и кодов подтверждения |

Создать базы и применить схемы из корня клона:

```powershell
createdb promscan_employees
createdb promscan_tasks
createdb promscan_credentials

psql -v ON_ERROR_STOP=1 -d promscan_employees -f database/sql/employees/001_schema.sql
psql -v ON_ERROR_STOP=1 -d promscan_tasks -f database/sql/tasks/001_schema.sql
psql -v ON_ERROR_STOP=1 -d promscan_credentials -f database/sql/credentials/001_schema.sql
```

Для удалённого сервера и локальных ролей используйте параметры `createdb`/`psql` или переменные libpq. SQL-наборы можно применять повторно; последующие изменения уже выпущенной схемы оформляйте новой миграцией. Скрипты не создают пользователей, демо-аккаунты, ключи или пароли.

Скрипты используют расширение PostgreSQL `pgcrypto` для `gen_random_uuid()`. На управляемом PostgreSQL его должен предварительно разрешить администратор; если политика сервера запрещает расширения, backend может генерировать UUID сам, но это нужно оформить отдельной миграцией до применения таблиц.

### Границы хранения

- `promscan.employees` хранит UUID, ФИО, нормализованный email, роль, активность, состояние приглашения и отметку подтверждения email. В таблице нет паролей или access key. UUID выдаёт PostgreSQL; демо-ID frontend вида `emp-003` не являются production-ID и при миграции заменяются UUID с сохранением таблицы соответствия вне этих схем.
- `promscan.reports` хранит поля `Report` из `docs/API_CONTRACT.md`: `equipment_id`, `inspection_id`, JSONB-снимок результата, статус, снимок имени исполнителя и временные отметки ремонта. Новые задачи создаются только в `open`; trigger разрешает `open → in_progress → closed`, требует назначенного сотрудника для начала и сам ставит время переходов.
- `promscan.access_key_credentials.key_hash` — полная PHC-строка Argon2id, включая соль и параметры алгоритма. Отдельная соль и открытый ключ не сохраняются. `auth_sessions.session_token_hash` хранит SHA-256-хеш случайного высокоэнтропийного токена, а не cookie/token в открытом виде. При изменении `key_hash` trigger автоматически отзывает все активные сессии и обновляет `key_created_at`. Короткий код подтверждения хранится как HMAC-SHA-256 (`bytea`) с отдельным секретом из secret manager, не как обычный быстрый или Argon2-хеш: это затрудняет офлайн-перебор короткого кода при утечке БД. Сравнение выполняйте в backend в constant time; коды должны быть одноразовыми, короткоживущими и защищёнными лимитом попыток.
- В API UUID передаются строками. Обычных внешних ключей между этими БД нет: PostgreSQL не поддерживает межбазовые FK. `reports.assignee_id` и `assignee_full_name` — неизменяемый по смыслу снимок на момент назначения. Backend проверяет активность сотрудника через `promscan_employees` до назначения и запуска задачи.
- Деактивируйте сотрудника, а не удаляйте запись, пока на него могут ссылаться задачи. При деактивации или перевыпуске ключа backend должен отозвать его сессии. Так как три базы не участвуют в одной транзакции, такие операции нужно оркестрировать в backend и сделать повторяемыми.

### Будущее подключение к backend/frontend

Эти схемы дополняют существующую базу `promscan` оборудования/измерений и не меняют её. Backend подключается к каждой базе отдельной серверной переменной, например `DATABASE_EMPLOYEES_URL`, `DATABASE_TASKS_URL` и `DATABASE_CREDENTIALS_URL`; имена переменных нужно согласовать при реализации сервера. Учётные данные подключения храните в secret manager или локальной конфигурации, не в Git. Frontend не подключается к PostgreSQL напрямую.

При реализации API сопоставьте `GET/POST /api/users` с `employees`, `POST /api/auth/login` с проверкой PHC-хеша и выдачей сессии, `GET/PATCH /api/reports` с `reports`. При создании задачи сначала проверьте сотрудника, затем сохраните `assignee_id` и `full_name` snapshot. Возвращая `AuthAccount`, соберите employee-поля и состояние приглашения из `promscan_employees`; никогда не возвращайте `key_hash`, `code_hash` или `session_token_hash`. Реализация backend должна также выполнять rate limiting входа, валидировать роли/RBAC и отзывать сессии при перевыпуске ключа.

Рекомендуется создать отдельную роль PostgreSQL для каждой базы и выдать backend только необходимые права на соответствующую DSN. Не давайте frontend-проекту ни одной DSN и не используйте одну суперпользовательскую роль в приложении.

Перед production применением согласуйте уникальность email и все три DSN в backend, примените схемы на тестовом PostgreSQL, проверьте полный цикл задачи, отказ для невалидного перехода и отзыв сессии. Для `Report.id` используйте строковое представление сгенерированного UUID; для `inspection_id` и `equipment_id` сохраняйте значения API-контракта. Пустые таблицы намеренны: демо-пользователи, демо-ключи и тестовые задачи из frontend не импортируются.

## Шаги: создать и заполнить PostgreSQL

1. Установить PostgreSQL 15 или новее и убедиться, что доступны `psql` и `createdb`.
2. Создать локальную базу:

   ```powershell
   createdb promscan
   ```

   Если требуется учётная запись, хост или порт, передайте их параметрами `createdb`/`psql` либо настройте стандартные переменные libpq. Пароли не записывать в этот репозиторий.

3. Выполнить файлы по порядку из корня клона:

   ```powershell
   psql -v ON_ERROR_STOP=1 -d promscan -f database/sql/001_schema.sql
   psql -v ON_ERROR_STOP=1 -d promscan -f database/sql/002_seed_pumps.sql
   psql -v ON_ERROR_STOP=1 -d promscan -f database/sql/003_measurements_schema.sql
   psql -v ON_ERROR_STOP=1 -d promscan -f database/sql/004_seed_measurement_catalog.sql
   psql -v ON_ERROR_STOP=1 -d promscan -f database/sql/005_measurement_views.sql
   ```

   Первые два файла можно запускать повторно: записи оборудования, характеристики, узлы и документы обновляются по естественным уникальным ключам. Файлы 003–005 также идемпотентны, но при изменении уже применённой схемы нужна отдельная миграция, а не повторный `CREATE TABLE IF NOT EXISTS`.

4. Проверить каталог:

   ```sql
   SELECT id, model, serial_number, inventory_number, state
   FROM promscan.equipment
   ORDER BY serial_number;

   SELECT e.serial_number, s.label, s.value, s.unit
   FROM promscan.equipment AS e
   JOIN promscan.equipment_specs AS s ON s.equipment_id = e.id
   ORDER BY e.serial_number, s.sort_order;

   SELECT count(*) AS maintenance_event_count
   FROM promscan.maintenance_records;
   ```

   Ожидаются четыре агрегата. История обслуживания сейчас пустая: заполненные в паспортах поля ввода в эксплуатацию и обслуживания не обнаружены.

5. Проверить показания и источники:

   ```sql
   SELECT count(*) AS measurement_channels
   FROM promscan.measurement_channels;

   SELECT id, provenance, import_status, source_row_count
   FROM promscan.measurement_import_batches
   ORDER BY id;

   SELECT count(*) AS loaded_measurements
   FROM promscan.measurements;

   SELECT c.id, t.level, t.comparison, t.threshold_value, c.unit
   FROM promscan.measurement_thresholds AS t
   JOIN promscan.measurement_channels AS c ON c.id = t.channel_id
   ORDER BY c.sort_order, t.level;

   SELECT * FROM promscan.v_measurement_batch_status ORDER BY id;
   ```

   Ожидается 7 каналов, 2 отклонённые demo-партии, 0 датчиков, 0 связей датчик–канал, 0 измерений, 0 диагнозов и 9 порогов. Пустая таблица измерений — намеренный результат: fake-показания не загружены.

### Проверки качества

- В каждом файле 500 строк данных и одна строка заголовка (всего 501 строка).

- Пустых ячеек нет, все числовые поля конечные.

### Почему строки не загружены

1. Данные выглядят синтетическими: ровный часовой шаг, одинаковые обороты в двух независимых файлах, правдоподобные, но слишком регулярные значения и готовые текстовые диагнозы.
2. Диапазон заканчивается `2026-12-01`, то есть в будущем относительно даты подготовки материалов (`2026-11-14`). Производственная телеметрия не может содержать будущие отметки.
3. Нет привязки к конкретному насосу, серийному номеру или физическому датчику. Загружать их как показания одного из четырёх насосов означало бы выдумать связь.
4. Нет часового пояса. Записывать локальное время как UTC нельзя.
5. Пользователь отдельно указал удалить fake-показания.

Поэтому две demo-партии зарегистрированы в `measurement_import_batches` со статусом `rejected`, а таблицы `measurements` и `measurement_diagnoses` оставлены пустыми. Метаданные сохранены для трассируемости: видно, какие файлы проверены и почему не приняты.

## Схема показаний

### `measurement_channels`

Логические величины, а не физические устройства: обороты, СКЗ, 1x, 2x, ВЧ шум, температура подшипника, температура обмоток. Для каждой заданы единица, модальность (`vibration`, `temperature`, `speed`), место измерения и описание.

### `sensor_devices`

Реестр физических датчиков для будущего внедрения: `equipment_id`, внешний идентификатор, производитель, модель, серийный номер, место установки, даты установки/вывода. В seed нет ни одного датчика, потому что источники не дают его идентификаторов.

### `sensor_channels`

Связь many-to-many: один физический датчик может отдавать несколько каналов (например, вибрационный анализатор — СКЗ, 1x, 2x и ВЧ шум), а один канал может быть доступен с нескольких датчиков. Составной внешний ключ в `measurements` не позволяет записать измерение канала, который не привязан к указанному датчику.

### `measurement_import_batches`

Манифест источника: провайдер, путь, файл, формат, происхождение (`synthetic_demo`, `unverified`, `verified_production`), статус (`catalogued`, `loaded`, `rejected`), число исходных строк, часовой пояс, наблюдаемый диапазон, оборудование и причина решения. Для загруженной партии обязателен `imported_at`; для отклонённой — `NULL`.

### `measurements`

Длинный формат: одна строка — одно значение канала в момент времени. Поля: партия, канал, необязательный датчик, `measured_at`, `numeric_value numeric(18,6)`, качество (`unverified`, `valid`, `suspect`, `invalid`). Уникальность `(batch_id, channel_id, measured_at)` защищает от дублей внутри партии; составной внешний ключ проверяет, что канал привязан к датчику через `sensor_channels`.

`measured_at` намеренно хранится как `timestamp without time zone`: в источниках нет часового пояса. Часовой пояс задаётся на уровне партии в `recorded_timezone`; backend должен преобразовывать его в UTC/`timestamptz` на границе API и явно указывать это в контракте.

### `measurement_diagnoses`

Текстовые диагнозы источника сохраняются отдельно от числовых измерений: модальность, время, исходная метка и нормализованный уровень (`normal`, `warning`, `alarm`, `unclassified`). Это историческая метка файла, а не серверный диагноз.

### `measurement_thresholds`

Пороги из DOCX с указанием исходного документа:

| Канал | Предупреждение | Тревога |
|---|---:|---:|
| Амплитуда 1x | > 2,8 мм/с | > 4,5 мм/с |
| Амплитуда 2x | > 1,8 мм/с | > 3,0 мм/с |
| ВЧ шум | > 2,5 g | не задан |
| Температура подшипника | > 75 °C | > 90 °C |
| Температура обмоток | > 90 °C | > 110 °C |

Проверка показала: все строки с метками «Пред:» и «Тревога:» в demo-файлах действительно превышают соответствующий порог. Это подтверждает согласованность описания и таблиц, но не делает ряды производственными.

### Представления

- `v_measurement_batch_status` — сколько строк реально загружено по каждой партии; у отклонённых demo-партий будет 0.
- `v_equipment_measurements` — измерения, связанные с подтверждённым оборудованием через физический датчик.
- `v_latest_equipment_measurement` — последнее не-invalid значение по каждому каналу оборудования.

### Что уже есть в репозитории

- `docs/API_CONTRACT.md` описывает оборудование, осмотры и задачи, но не содержит эндпоинтов или схем показаний датчиков.
- `src/lib/inspection.ts` содержит `ConditionParameters` — вероятности `oil_leak`, `rust`, `poor_weld` от vision-модели. Это не физические измерения и не история телеметрии; смешивать их нельзя.
- Каталог оборудования и показания в этой ветке не связаны с frontend-кодом. Существующий frontend mock-слой не удалялся; его замена выполняется отдельно после появления backend API.

## Источник и качество паспортных данных

Источник основных характеристик — четыре сканированных файла `1) Насос №1 ПС.pdf` … `1) Насос №4 ПС.pdf` в папке `Документация/Паспорта Насосов` на предоставленном Яндекс.Диске. Все четыре паспорта описывают модель `AMS PCP60S12/3 01 Ex B1 HNBR DTS`; серийные номера — `21031004-1` … `21031004-4`. Технические таблицы содержат одинаковые значения. Оригиналы являются сканами, поэтому перед эксплуатационным применением критичные величины нужно сверить с читаемым экземпляром паспорта.

Из документов не выводились значения, которых в них нет или которые не заполнены: инвентарный номер, местоположение, состояние оборудования, дата ввода в эксплуатацию, срок службы и события ТОиР. Поэтому соответствующие поля в seed оставлены `NULL`; записи в `maintenance_records` не добавлены. Не задавайте им фиктивные значения только ради заполнения API.

### Подключение реальных датчиков и показаний

1. Получить утверждённый перечень физических датчиков: к какому оборудованию относится каждый, заводской/внешний ID, место установки, единица, даты поверки/калибровки. Заполнить `sensor_devices`, затем `sensor_channels` — по одной строке на каждый измеряемый канал. ID не выдумывать.
2. Для каждого файла/потока создать `measurement_import_batches` с `provenance = 'unverified'`, указав `recorded_timezone` и `equipment_id`. Не помечать партию `verified_production` до сверки с источником.
3. Импортировать данные транзакционно: привести значения к единицам каналов, проверить конечность чисел, диапазон дат, дубли `(batch, channel, measured_at)`, пропуски и выбросы. Ошибки сохранять в лог импорта; не подменять их нулями.
4. После проверки перевести партию в `loaded`, выставить `imported_at` и присвоить измерениям `quality_status` (`valid`, `suspect`, `invalid`). Отклонённые строки не должны попадать в `v_equipment_measurements` как достоверные.
5. Для API добавить новые эндпоинты, сначала обновив `docs/API_CONTRACT.md`, TypeScript-типы и Pydantic-схемы. Предлагаемая минимальная форма (требует согласования, а не является текущим контрактом):
   - `GET /api/measurement-channels` — список каналов и единиц;
   - `GET /api/equipment/{equipment_id}/measurements?channel_id=...&from=...&to=...` — точки временного ряда с пагинацией;
   - `GET /api/equipment/{equipment_id}/measurements/latest` — последнее значение по каналам.
6. В ответах явно указывать единицу, `measured_at` с часовым поясом/UTC и `quality_status`. Не смешивать `ConditionParameters` (вероятности oil leak/rust/poor weld от vision-модели) с физическими показаниями датчиков: это разные сущности.
7. Frontend не подключать к PostgreSQL. Он должен получать данные только через backend API; для графиков/таблиц показаний нужен новый UI-компонент, которого сейчас нет. Существующий mock-слой не удалён и остаётся до готовности совместимого backend.
8. Исторические метки `measurement_diagnoses` не выдавать за текущее состояние оборудования. Серверная диагностика по порогам — отдельная согласованная логика с версией правил и журналом срабатываний.
9. Прогнать проверки на тестовой PostgreSQL: применение с нуля, повторный запуск seed, ограничения уникальности, запросы последнего значения, пагинация длинных рядов, корректность часовых поясов и поведение при пустой истории.

### Шаблон загрузки реальной CSV-партии

Ниже — ориентир для backend-агента и ручной проверки. Это не готовый production-загрузчик и не разрешение запускать его с demo-файлами. Пути, ID и часовой пояс подставляются из подтверждённого источника.

```sql
BEGIN;

INSERT INTO promscan.measurement_import_batches (
    id, dataset_code, source_provider, source_path, source_file, source_format,
    provenance, import_status, source_row_count, recorded_timezone,
    observed_start, observed_end, equipment_id, source_description
) VALUES (
    'import-2026-11-14-vibration-01', 'vibration', 'local',
    'incoming/vibration.csv', 'vibration.csv', 'csv',
    'unverified', 'catalogued', 0, 'Asia/Yekaterinburg',
    NULL, NULL, 'pump-ams-pcp60s12-3-01-1', 'Партия из подтверждённого источника'
);

CREATE TEMP TABLE measurement_stage (
    sensor_external_identifier text NOT NULL,
    channel_id                 text NOT NULL,
    measured_at                timestamp NOT NULL,
    numeric_value              numeric(18, 6) NOT NULL,
    quality_status             text NOT NULL
) ON COMMIT DROP;

\copy measurement_stage FROM 'incoming/vibration.csv' WITH (FORMAT csv, HEADER true, ENCODING 'UTF8')

INSERT INTO promscan.measurements (
    batch_id, channel_id, sensor_id, measured_at, numeric_value, quality_status
)
SELECT
    'import-2026-11-14-vibration-01',
    st.channel_id,
    sd.id,
    st.measured_at,
    st.numeric_value,
    st.quality_status
FROM measurement_stage AS st
JOIN promscan.sensor_devices AS sd
    ON sd.external_identifier = st.sensor_external_identifier
JOIN promscan.sensor_channels AS sc
    ON sc.sensor_id = sd.id AND sc.channel_id = st.channel_id
ON CONFLICT (batch_id, channel_id, measured_at) DO NOTHING;

DO $$
DECLARE
    expected_rows integer;
    loaded_rows integer;
BEGIN
    SELECT count(*) INTO expected_rows FROM measurement_stage;
    SELECT count(*) INTO loaded_rows
    FROM promscan.measurements
    WHERE batch_id = 'import-2026-11-14-vibration-01';

    IF loaded_rows <> expected_rows THEN
        RAISE EXCEPTION
            'Загружено % из % строк: проверьте дубли, датчики и связи каналов',
            loaded_rows, expected_rows;
    END IF;
END $$;

UPDATE promscan.measurement_import_batches AS b
SET source_row_count = s.row_count,
    observed_start = s.observed_start,
    observed_end = s.observed_end,
    import_status = 'loaded',
    imported_at = now()
FROM (
    SELECT count(*) AS row_count, min(measured_at) AS observed_start, max(measured_at) AS observed_end
    FROM promscan.measurements
    WHERE batch_id = 'import-2026-11-14-vibration-01'
) AS s
WHERE b.id = 'import-2026-11-14-vibration-01';

COMMIT;
```

Если backend загружает данные драйвером, а не через `psql`, те же действия выполняются в одной транзакции: batch → staging/COPY → проверка количества и связей → `measurements` → обновление batch. При несовпадении количества транзакция должна откатиться, а не помечать партию `loaded`.

## Проверка на PostgreSQL

Материалы проверены 14.11.2026 на изолированном PostgreSQL 18.7 (portable Windows x64 binaries). Системный `psql` и Docker в окружении отсутствуют, поэтому проверка выполнялась на временном локальном кластере, а не на удалённом сервере.

- Все пять SQL-файлов применены к пустой базе `promscan` без ошибок.
- Повторный запуск файлов 001–005 прошёл успешно: схема и seed идемпотентны.
- После применения: 4 единицы оборудования, 48 характеристик, 24 узла, 44 характеристики узлов, 7 каналов, 2 отклонённые demo-партии, 0 датчиков, 0 измерений и 9 порогов.
- Тестовая транзакция создала датчик, привязала к нему два канала, создала партию и измерение; `v_latest_equipment_measurement` вернуло `1.020000 мм/с`; затем транзакция откатана.
- Шаблон CSV-загрузки проверен отдельно: две строки из CSV загрузились, партия получила `loaded`, `source_row_count = 2`, а `v_equipment_measurements` вернуло оба канала. Тестовые записи после проверки удалены.
- Ограничения проверены: повтор измерения `(batch, channel, measured_at)` отклонён unique-констрейнтом; партия `loaded` без `imported_at` отклонена check-констрейнтом.
- Целевая версия схемы — PostgreSQL 15+; отдельный прогон на PostgreSQL 15 не выполнялся. Синтаксис всех файлов дополнительно проверен парсером PostgreSQL (`pglast`).

Дополнительные схемы сотрудников/задач/учётных данных проверены на отдельном временном PostgreSQL 18.7:

- три базы (`promscan_employees`, `promscan_tasks`, `promscan_credentials`) созданы с нуля, каждый SQL-файл применён повторно без ошибок;
- проверены нормализованный email и состояния приглашения, а также отказ невалидного состояния;
- задача прошла `open → in_progress → closed`, серверные timestamps выставились trigger-ом, обратный переход `closed → open` отклонён;
- после замены `key_hash` активная сессия получила `revoked_at`, а открытые ключи и тестовые сотрудники в базы не загружались.

## Ограничения этой заготовки

- Это SQL-схема, каталог источников и проверенные паспортные данные, а не запущенный сервер или уже созданный удалённый экземпляр PostgreSQL.
- Прогон выполнен только на временном локальном PostgreSQL 18.7; удалённый или целевой экземпляр не создавался. На PostgreSQL 15 миграции не запускались.
- Seed покрывает только четыре одинаковых винтовых насоса. Остальные документы в папке включают редукторы, электродвигатели, инструкции и сертификаты; они не импортируются как отдельные изделия без проверки связи с конкретным насосом.
- Показания датчиков отсутствуют намеренно: оба Excel-файла признаны synthetic demo и отклонены. Реальные данные должны прийти из подтверждённого источника с ID оборудования, датчика и часовым поясом.
- В проекте существуют отдельные API-заготовки и упоминания другого TOiР backend. Их маршруты/модели нужно сверить с `docs/API_CONTRACT.md` до интеграции; эта база сама по себе не делает backend совместимым.
