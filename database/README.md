# База данных насосов PromScan

Этот каталог содержит только PostgreSQL-артефакты и инструкцию к ним. Backend не входит в эту ветку. Ветка `database` создана независимо (orphan) и не содержит историю или файлы frontend.

## Состав

- `sql/001_schema.sql` — схема `promscan` и таблицы каталога, характеристик, узлов, документов и истории обслуживания.
- `sql/002_seed_pumps.sql` — идемпотентное добавление четырёх агрегатов AMS PCP60S12/3 и данных, переписанных из паспортов.

PDF-паспорта в Git не добавлены. В таблице документов сохраняются имя и исходный путь на Яндекс.Диске; это метаданные, а не URL для скачивания. В рабочей системе файлы следует хранить в согласованном объектном хранилище или документном сервисе.

## Шаги: создать и заполнить PostgreSQL

1. Установить PostgreSQL 15 или новее и убедиться, что доступны `psql` и `createdb`.
2. Создать локальную базу:

   ```powershell
   createdb promscan
   ```

   Если требуется учётная запись, хост или порт, передайте их параметрами `createdb`/`psql` либо настройте стандартные переменные libpq. Пароли не записывать в этот репозиторий.

3. Создать таблицы и индексы из корня клона:

   ```powershell
   psql -v ON_ERROR_STOP=1 -d promscan -f database/sql/001_schema.sql
   ```

4. Загрузить четыре насоса, паспортные характеристики, компоненты и ссылки-источники:

   ```powershell
   psql -v ON_ERROR_STOP=1 -d promscan -f database/sql/002_seed_pumps.sql
   ```

   Seed можно запускать повторно: записи оборудования, характеристики, узлы и документы обновляются по естественным уникальным ключам. Перед повторным импортом отредактированных паспортных данных проверьте изменения в SQL.

5. Проверить результат:

   ```sql
   SELECT id, model, serial_number, inventory_number, state
   FROM promscan.equipment
   ORDER BY serial_number;

   SELECT e.serial_number, s.label, s.value, s.unit
   FROM promscan.equipment AS e
   JOIN promscan.equipment_specs AS s ON s.equipment_id = e.id
   ORDER BY e.serial_number, s.sort_order;

   SELECT count(*) AS maintenance_event_count
   FROM promscan.maintenance_records;
   ```

   Ожидаются четыре агрегата. История обслуживания сейчас пустая: заполненные в паспортах поля ввода в эксплуатацию и обслуживания не обнаружены.

## Источник и качество данных

Источник основных характеристик — четыре сканированных файла `1) Насос №1 ПС.pdf` … `1) Насос №4 ПС.pdf` в папке `Документация/Паспорта Насосов` на предоставленном Яндекс.Диске. Все четыре паспорта описывают модель `AMS PCP60S12/3 01 Ex B1 HNBR DTS`; серийные номера — `21031004-1` … `21031004-4`. Технические таблицы содержат одинаковые значения. Оригиналы являются сканами, поэтому перед эксплуатационным применением критичные величины нужно сверить с читаемым экземпляром паспорта.

Из документов не выводились значения, которых в них нет или которые не заполнены: инвентарный номер, местоположение, состояние оборудования, дата ввода в эксплуатацию, срок службы и события ТОиР. Поэтому соответствующие поля в seed оставлены `NULL`; записи в `maintenance_records` не добавлены. Не задавайте им фиктивные значения только ради заполнения API.

## Шаги будущего подключения к приложению

1. Backend-агент переносит каталог `database/` из ветки `database` в репозиторий backend. Например, находясь в целевой ветке общего репозитория, можно получить только этот каталог командой `git checkout database -- database/`; затем проверить diff и создать отдельный коммит. Это не переносит frontend-файлы.
2. Настроить backend-подключение через переменную окружения `DATABASE_URL`; секреты и реальные пароли хранить в локальном `.env`/secret manager, не в Git. Backend подключается к PostgreSQL; браузер/frontend к БД напрямую не подключается.
3. Реализовать миграции и слой репозитория поверх `promscan.equipment`, `equipment_specs`, `equipment_nodes` и `node_specs`. Выдавать `EquipmentSummary` и `EquipmentDetail` в форме, описанной в `docs/API_CONTRACT.md` frontend-проекта.
4. До включения API согласовать контрактные несовпадения: frontend требует строковые `inventory_number`, `location` и `state`, но паспорта не содержат первые два значения и не задают текущее состояние. Либо эти значения заполняются из утверждённого реестра оборудования, либо меняются API/Pydantic/TypeScript-схемы на nullable; состояние нельзя угадывать.
5. Обновить API-контракт и TypeScript-типы согласованно. Существующие mock ID и пример `pump-cns-38-220` не являются ID этих агрегатов. Для подключения использовать реальные `pump-ams-pcp60s12-3-01-N` либо добавить согласованный внешний ID/маппинг; не подменять серийный номер инвентарным.
6. Backend сериализует строки `equipment_specs` и `node_specs` как массивы `{label, value, unit}` с сортировкой по `sort_order`. `equipment_nodes.id` используется как `node_id`; перед отдачей результата осмотра backend проверяет, что такой узел относится к выбранному оборудованию.
7. Загружать оригиналы паспортов в документное хранилище, добавить долговременный ключ объекта и выдавать приложению контролируемый URL. Не использовать краткоживущую ссылку скачивания Яндекс.Диска как постоянный `document_url`.
8. Заполнять `maintenance_records` только подтверждёнными событиями из журнала ТОиР. При подключении истории согласовать отдельный API-ответ: текущий frontend-контракт не описывает maintenance history.
9. Проверить миграции и запросы на тестовой PostgreSQL, сверить API с OpenAPI и прогнать frontend-тесты. Только после этого переключать клиент из mock-режима; не включать `VITE_USE_MOCK_API=false` до готовности совместимого backend.

## Ограничения этой заготовки

- Это SQL-схема и проверенные паспортные исходные данные, а не запущенный сервер или уже созданный удалённый экземпляр PostgreSQL.
- В окружении автора изменений `psql`/Docker не обнаружены, поэтому фактическое применение к серверу PostgreSQL здесь не подтверждалось.
- Seed покрывает только четыре одинаковых винтовых насоса. Остальные документы в папке включают редукторы, электродвигатели, инструкции и сертификаты; они не импортируются как отдельные изделия без проверки связи с конкретным насосом.
- В проекте существуют отдельные API-заготовки и упоминания другого TOiР backend. Их маршруты/модели нужно сверить с `docs/API_CONTRACT.md` до интеграции; эта база сама по себе не делает backend совместимым.
