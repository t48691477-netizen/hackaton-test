# ПромСкан — веб-панель промышленного зрения

**ПромСкан — frontend веб-панели на React + TypeScript + Vite** для осмотра
оборудования, отображения дефектов и работы диспетчера. Сейчас панель
работает автономно на заглушках: реальные модели, LLM и сохранение данных
не подключены.

**Backend ещё не реализован для текущей панели.** Серверный прототип удалён
пользователем; в репозитории остался только frontend. Реальный backend будет
добавлен отдельным агентом по ТЗ и отдельной задаче. Ниже — задание и порядок
подключения, а не описание уже работающего сервера. Создавать серверную часть
в этом репозитории без отдельного поручения нельзя.

Главный документ для интеграции: [`docs/API_CONTRACT.md`](docs/API_CONTRACT.md).
Он является источником истины по схемам. Если меняется API — сначала
обновляется контракт, затем TypeScript-типы в `src/lib/inspection.ts` и,
в будущем серверном проекте, Pydantic-схемы.

## 1. Быстрый старт

Нужны Node.js и npm. Команды выполняются из корня этого проекта:

```bash
npm install
npm run dev
```

Открыть: <http://127.0.0.1:5173/>

- Демо-ключ директора: `PSCDRT2345` (10 символов).
- После входа директор попадает в `/users`, диспетчер — в `/scanner`,
  рабочий — тоже в `/scanner`: веб-панель даёт ему только сканер.
- Вход выполняется по индивидуальному 10-значному ключу. Ключи сотрудников
  создаёт директор или администратор; в `localStorage` хранятся только соль
  и PBKDF2-хеш. Открытый ключ администратору не показывается — он уходит
  сотруднику письмом на email.
- Сессия лежит в `sessionStorage` и действует только в текущей вкладке.
  Новая вкладка снова просит ключ. Это демо-модель, а не серверная
  аутентификация.
- Для автономной работы `.env` не обязателен: mock-режим включён по умолчанию.
  При необходимости скопировать [`.env.example`](.env.example) в `.env`.

| Алексей Смирнов | рабочий | `PSCENG5542` |

Все ключи выше — публичные ключи демо-стенда. В production их нельзя хранить

**Проверка с телефона в локальной сети.** Запустить Vite с доступом по сети:

```bash
npm run dev:lan
```

Vite напечатает `Network: https://<IP-компьютера>:5173/`. Телефон должен быть
в той же Wi-Fi-сети. Сертификат самоподписанный, поэтому браузер один раз
покажет предупреждение — выбрать «Перейти на сайт» / «Дополнительно → Перейти».
HTTPS здесь обязателен: по `http://` браузер отключает WebCrypto (проверку
ключа) и камеру на телефоне. Если открыть `http://IP:5173`, панель честно
скажет, что WebCrypto недоступен, вместо «ключ не подошёл».

Для проверки ролей используйте seed-ключи из таблицы выше: сотрудники,
созданные через интерфейс, живут только в браузере, где их создали.

Демо-задача сотрудника открывается по прямой ссылке
[`/task/report-1042`](http://127.0.0.1:5173/task/report-1042) — она доступна
без роли и не требует входа в веб-панель. Это мобильный экран для сценария
«взял в работу → выполнил»; ссылку на конкретную задачу выдаёт сканер после
передачи.

Проверки:

```bash
npm run build
npm audit
```

Запуск серверной части для демо **не нужен**. Переключение на будущий API
описано в разделе 7; один флаг окружения не подключает сотрудников,
аутентификацию и панель дефектов автоматически.

## 2. Что уже работает

### Роли и ключи

| Роль | Доступ |
|---|---|
| `director` | `/scanner`, `/defects`, `/users`; создаёт ключи, включая администраторов |
| `admin` | `/scanner`, `/defects`, `/users`; создаёт диспетчеров и рабочих |
| `dispatcher` | `/scanner`, `/defects` |
| `engineer` | только `/scanner`; прямой переход на `/defects` и `/users` даёт 403. Отдельно доступна демо-карточка `/task/{id}` |

Прямой переход диспетчера на `/users`, а рабочего — на `/defects` или
`/users` показывает экран 403 на клиенте,
а не серверный HTTP-ответ. Неизвестная/битая сессия считается отсутствием
входа. Сессия хранится в `sessionStorage` (`promscan:session:v1`) и содержит
только `accountId`, ФИО, email, роль и время выдачи; ключ в ней не хранится.
Новая вкладка не наследует сессию и снова показывает форму ключа.
Рабочему в веб-панели доступен только сканер. `/task/{id}` остаётся
отдельным мобильным экраном: в реальном продукте его заменит нативное
приложение, а сейчас он нужен, чтобы показать весь сценарий ремонта в браузере.

Права заданы в `src/lib/roles.ts` (`ROLE_PERMISSIONS`): `scan`, `dispatch`,
`users`. Это только UI-модель; backend обязан проверять те же права на каждом
запросе. Мобильное приложение описано отдельно и не входит в веб-права.

### Ключи и приглашения

- Ключ — 10 символов из алфавита `A-HJ-NP-Z2-9` (без `I`, `O`, `0`, `1`),
  генерируется через `crypto.getRandomValues`.
- В хранилище (`promscan:employees:v2`) лежат `keySalt` и `keyHash`
  (PBKDF2-SHA-256, 120 000 итераций), но не сам ключ.
- Ключ **не показывается администратору**: ни при создании, ни при
  перевыпуске. Он сразу уходит в письмо на email сотрудника. В таблице
  отображается только маска `•••••-•••••`.
- Перевыпуск заменяет хеш: старый ключ перестаёт работать для новых входов.
  Активные вкладки в демо не отзываются — это ограничение описано в
  `SECURITY.md`; в production сервер обязан отозвать все сессии сотрудника.
- В демо `sendAccessKeyEmail()` не отправляет письмо, а складывает его в
  mock-outbox `promscan:mail-outbox:v1` в `localStorage` и возвращает
  `queued`. Интерфейс администратора outbox не читает.

**Как открыть демо-письмо с ключом нового сотрудника.** Это имитация почты
сотрудника, а не часть панели администратора:

1. DevTools → Application → Local Storage → ключ
   `promscan:mail-outbox:v1`.
2. В массиве найдите последнее письмо: `to`, `fullName`, `accessKey`,
   `confirmationCode`, `body`.
3. Введите `accessKey` на экране входа. Письмо хранит последние 20 сообщений.

В production mock-outbox удаляется: ключ генерирует сервер, хранит только
Argon2id-хеш и отправляет письмо через SMTP/Gmail API. Ответ API не содержит
`access_key`.

- Вход выполняется локально: `authenticateAccessKey()` перебирает аккаунты,
  проверяет PBKDF2-хеш и создаёт сессию. В production эту работу выполняет
  backend, а ключ передаётся только по HTTPS.

### Сценарий ремонта

1. Диспетчер открывает `/scanner`, наводит камеру на агрегат. Сканер сам
   находит дефекты и показывает **рекомендацию по восстановлению повреждённого
   узла** (шаги из `result.llm.recommendation_steps`).
2. В блоке «Передача задачи» диспетчер выбирает исполнителя, при необходимости
   пишет комментарий и прикладывает фото, затем нажимает «Передать задачу».
   Создаётся `Report` со статусом `open`; в ответе приходит `assignee`.
3. Сканер показывает ссылку `/task/{report.id}`. Её можно открыть на телефоне
   или во второй вкладке браузера; кнопка «Скопировать ссылку» копирует
   абсолютный URL.
4. Сотрудник нажимает «Выполнить задачу» — `PATCH /api/reports/{id}/status`
   переводит задачу в `in_progress`, проставляется `started_at`. Диспетчер
   в `/defects` видит «В работе» и имя сотрудника.
5. Сотрудник оставляет комментарий и нажимает «Отметить выполненной» — задача
   становится `closed`, проставляются `completed_at` и `repair_comment`.
   Диспетчер видит «Выполнено» у того же сотрудника.
6. В mock-режиме задачи лежат в `localStorage` и синхронизируются между
   вкладками. В real-режиме источником истины должен быть backend.

Это демонстрация контракта, а не защищённый процесс: ключ проверяется в
браузере, а действие с задачей не привязано к вошедшему сотруднику. Реальные
сессии, проверка «действие выполняет назначенный сотрудник» и серверный
справочник пользователей — отдельная задача.

### Веб-сканер

- Камера через `getUserMedia`, `<video>`, fallback на загрузку фото.
- **Кнопки «Анализировать» нет.** Распознавание запускается автоматически:
  первая попытка через ~0,5 с, далее попытки каждые ~1,8 с. Пока предыдущий
  запрос выполняется, следующий пропускается; скорость реального API этим
  не гарантируется. Загруженное фото анализируется один раз.
- Дефекты показываются рамками (`bbox`) и SVG-полигонами (`polygon`).
- Наведение курсором на рамку или строку дефекта справа открывает
  **паспортные характеристики узла** из карточки оборудования: материал,
  толщина стенки, давление, ресурс, момент затяжки и т. д. (сейчас заглушки).
  Характеристик самого дефекта (длина трещины, раскрытие, глубина, допуск)
  нет — модели их не предсказывают.
- Постоянного блока «Паспорт оборудования» нет: характеристики показываются
  только при наведении, фокусе или выборе конкретного дефекта. До этого
  справа видна подсказка.
- Клик по дефекту фиксирует выбор. Наведение временно показывает другой
  узел, уход курсора возвращает зафиксированный выбор либо подсказку.
  Выбор очищается при сбросе или загрузке нового источника.
- На планшете и телефоне правая панель уходит под камеру и не зажимается в
  узкую колонку: характеристики и форма читаются в один столбец. На ПК
  панель становится шире, а карточки внутри неё не переполняются.
- После результата показывается «Рекомендация по восстановлению» с шагами
  для повреждённого узла и форма «Передача задачи»: исполнитель, комментарий,
  необязательное фото. Отдельного выбора статуса нет — новая задача всегда
  `open`, её начинает и завершает сотрудник.
- После успешной передачи видны имя исполнителя и ссылки «Открыть задачу» /
  «Скопировать ссылку»; ошибка сохранения не теряет выбранного
  исполнителя и позволяет повторить отправку.
- Сейчас любые кадры дают одни и те же три демо-дефекта. Камера и загрузка
  фото настоящие, распознавание — нет. ID агрегата в сканере фиксирован.

### Сотрудники

- Таблица: ФИО, Email, Роль, Ключ доступа. Колонки «Статус» нет.
- Добавление сотрудника в боковой панели, фиксированный футер.
- Роль выбирается из `admin / dispatcher / engineer`; администратора может
  создать только директор.
- Ключ генерируется криптографически и отправляется на email сотрудника.
  Администратор не видит и не копирует ключ; в таблице только маска.
- После создания и перевыпуска показывается подтверждение «Письмо с ключом
  в очереди» без самого ключа. Демо-письмо лежит в mock-outbox (см. выше).
- Ключи администраторов перевыпускает только директор; администратор может
  перевыпускать диспетчеров и рабочих.
- Для каждого сотрудника показывается статус письма: «отправлено», «в
  очереди», «не отправлено» или «не отправлялось».
- Четыре начальные записи и добавленные сотрудники живут в общем демо-
  справочнике `src/lib/employees.ts` и `localStorage`
  (`promscan:employees:v2`), поэтому переживают перезагрузку страницы.
- Исполнители задач выбираются из этого же справочника через `getEngineers()`,
  чтобы имя на странице сотрудников и в задаче не расходилось.
- Сотрудники, созданные в UI, существуют только в браузере, где их создали.
  Для проверки на телефоне и в другом браузере используйте seed-ключи из
  раздела 1.
- Реальная выдача учётных записей, отправка писем и серверный вход не
  реализованы: это заготовки, описанные в разделах 5–7.

### Дефекты

- Сводка по общему числу, критическим, находящимся в работе и выполненным.
- Таблица задач: дефект, оборудование, приоритет, статус, исполнитель, время.
  Статусы: «Открыт», «В работе», «Выполнено».
- Данные демонстрационные (см. реестр заглушек) и загружаются через
  `fetchReports()` + `fetchEquipment()` из `src/lib/api.ts`: есть состояния
  загрузки, ошибки с кнопкой «Повторить» и пустого списка.
- Исполнитель берётся из `report.assignee.full_name`; «Не назначен»
  показывается только для задачи без назначения и помечено `data-mock`.
- У каждой строки есть ссылка «Открыть» на `/task/{report.id}`.
- Кнопка «Обновить», автообновление при возврате фокуса на вкладку и подписка
  на изменения mock-задач: после действия сотрудника в соседней вкладке
  панель перечитывает список. В real-режиме подписка не активна — нужен
  `GET /api/reports` (при необходимости polling или WebSocket по отдельному
  согласованию).
- Блока «Паспорт оборудования» на странице нет: он удалён по требованию.
- Задачи, созданные в сканере, сохраняются в mock-режиме в `localStorage`
  (`promscan:mock-reports:v2`) и переживают перезагрузку вкладки; в памяти
  сервера их пока нет. После подключения backend источником истины станет
  `GET /api/reports`.

### Карточка задачи сотрудника

- Отдельный мобильный маршрут `/task/{id}` вне `Layout`: без боковой
  навигации, с брендом и статусом. Открывается для `engineer` и без сессии
  как демо-ссылка; после интеграции должен быть защищён сессией или заменён
  нативным приложением.
- Показывает оборудование, инвентарный номер, локацию, дефект, узел,
  рекомендацию по восстановлению, исполнителя и даты.
- `open` → кнопка «Выполнить задачу»; после неё статус «В работе» и кнопка
  «Отметить выполненной».
- `in_progress` → комментарий к выполнению (необязательно) и кнопка
  «Отметить выполненной».
- `closed` → сообщение «Задача выполнена» без кнопок.
- Если исполнителя нет, действия заблокированы с подсказкой, что задачу
  назначает диспетчер.
- Экран — демо-замена мобильного приложения. Ссылку на него формирует сканер;
  в real-режиме действия должен авторизовать backend по сессии сотрудника.

### Дизайн

- Светлая «серебристая» тема в духе рекламы MacBook: тёплый фон `#F6F5F2`,
  белые панели, графитовый текст, тонкие линии.
- Сигнальный оранжевый `#C2410C` как единственный акцент.
- IBM Plex Sans + IBM Plex Mono, острые углы, техническая типографика.
- Камера остаётся тёмной для контраста снимка и рамок дефектов.
- Адаптив: 1440 / 1024 / 768 / 390, мобильное меню, доступность с клавиатуры.

## 4. Реестр заглушек

Реестр включает фиктивные данные, недостающие сервисы и настоящие клиентские
механизмы, которые пока обслуживают демо. Статус означает **готовность точки
замены**, а не готовность backend:

## 5. Контракт API (кратко)

Полные схемы и примеры: [`docs/API_CONTRACT.md`](docs/API_CONTRACT.md).

Это **целевой** контракт, сервер сейчас недоступен в составе проекта.
Пример будущего базового URL: `http://127.0.0.1:8000`.

| Метод | Путь | Вход → ответ | Успех |
|---|---|---|---|
| GET | `/api/equipment` | → `EquipmentSummary[]` | 200 |
| GET | `/api/equipment/{id}` | → `EquipmentDetail` с узлами и `specs` | 200 |
| POST | `/api/equipment` | JSON `EquipmentUpsert` → `EquipmentDetail` | 201 создание / 200 обновление |
| POST | `/api/inspect` | multipart с фото → `InspectionResult` с `Defect[]`, LLM и `meta` | 200 |
| POST | `/api/reports` | multipart с результатом осмотра и `assignee_id` → `Report` | 201 |
| GET | `/api/reports` | query `status` опционален → `Report[]` | 200 |
| GET | `/api/reports/{id}` | → `Report` для карточки `/task/{id}` | 200 |
| PATCH | `/api/reports/{id}/status` | JSON `{status, comment?}` → обновлённый `Report` | 200 |
| POST | `/api/auth/login` | JSON `{access_key}` → сессия + `AuthAccount` | 200 |
| POST | `/api/auth/logout` | отзыв сессии | 204 |
| GET | `/api/auth/me` | текущий `AuthAccount` | 200 |
| GET/POST | `/api/users` | список / создание сотрудника и ключа | 200 / 201 |
| POST | `/api/users/{id}/reissue-key` | новый ключ, старый инвалидируется | 200 |
| POST | `/api/users/{id}/invite` | письмо с ключом/кодом | 202 |
| POST | `/api/auth/confirm-email` | код подтверждения email | 200 |

`POST /api/reports` создаёт задачу в статусе `open` и сохраняет исполнителя
снимком `{id, full_name}`. `PATCH` выполняет только переходы
`open → in_progress → closed`: повтор того же статуса идемпотентен,
недопустимый переход — `409`. В реальном сервисе исполнитель определяется
сессией и проверяется на сервере. Endpoint'ы доступа — целевой контракт из
`docs/API_CONTRACT.md`, раздел 4.1; сервер их ещё не реализует.

### Ключевые правила

- Все координаты нормализованы `0..1`, начало — левый верхний угол.
- `bbox`: `[x_min, y_min, x_max, y_max]`.
- `polygon`: `[[x, y], ...]`, минимум три точки, контур замыкается при
  отрисовке; `null`, если есть только бокс. Не путать bbox с форматом YOLO
  `[x_center, y_center, width, height]` или пиксельными координатами.
- `x_min < x_max`, `y_min < y_max`; `confidence` — `0..1`.
- `node_id` — ID узла в `equipment.nodes` либо `null`. Паспортные
  характеристики — из узла, не вычисленные размеры дефекта.
- `severity` / `criticality`: `low | medium | high`.
- `ReportStatus`: `open | in_progress | closed`; UI: «Открыт», «В работе»,
  «Выполнено».
- `Report` хранит `assignee: {id, full_name} | null`, `started_at`,
  `completed_at`, `repair_comment`.
- Ключ доступа — ровно 10 символов `A-HJ-NP-Z2-9`; в хранилище только соль и
  PBKDF2-хеш. Роли: `director | admin | dispatcher | engineer`; рабочему
  в веб-панели доступен только сканер.
- JSON использует `snake_case`, время — ISO 8601 UTC.
- `POST /api/inspect` — `multipart/form-data`: обязательные `file`
  (JPEG/PNG/WebP) и `equipment_id`. Ответ синхронный, без ID фоновой задачи.
- `POST /api/reports` — `multipart/form-data`: `equipment_id`,
  `inspection_id`, `status` (веб-панель передаёт `open`), `payload`
  (обязательная JSON-строка `InspectionResult`); `comment`, файл `photo`
  и `assignee_id` опциональны.
- `PATCH /api/reports/{id}/status` — JSON: `status` только
  `in_progress | closed`, `comment` опционален и сохраняется в
  `repair_comment` при завершении. Клиент не передаёт `assignee_id`:
  backend берёт сотрудника из сессии и проверяет права.
- `POST /api/auth/login` — JSON `{access_key}`. Ответ содержит HttpOnly-сессию
  и `AuthAccount` без хеша/соли/ключа. Неверный ключ — `401`, частые попытки —
  `429`.
- `POST /api/users` — доступ `director | admin`; создаёт ключ, сохраняет хеш,
  отправляет ключ письмом и возвращает только `account` + `invitation`.
  `access_key` в ответе отсутствует. `admin` не может создавать `admin` или
  `director`; перевыпуск ключей администраторов — только у `director`.
- При отправке `FormData` не задавать `Content-Type` вручную: браузер добавит
  multipart boundary. `src/lib/api.ts` уже делает это правильно.
- Ошибки: `404` — объект не найден, `422` — валидация, `503` — недоступная
  модель/LLM в запрошенном real-режиме; `detail` должен объяснять причину.
- `meta.processing_ms` — измеренная сервером длительность; `vision_mode` и
  `llm_mode` независимо отражают фактически использованные режимы. Получение
  ответа по HTTP само по себе не означает, что модели работают в real.

## 6. Требования к будущему backend по ТЗ

Это задание **следующему агенту после отдельного поручения**, без реализации
в текущем репозитории. Нужно подготовить FastAPI-сервис с endpoint'ами
`GET/POST /api/equipment`, `GET /api/equipment/{id}`, `POST /api/inspect`,
`POST/GET /api/reports`, `GET /api/reports/{id}`,
`PATCH /api/reports/{id}/status`, endpoint'ами доступа из раздела 4.1
контракта и схемами из контракта.

### 6.1. Пайплайн моделей

1. Подключить модели и проверить реальные артефакты, классы и типы выходов:
   - `Decizez/yolov-corrosion-detection` — сегментация коррозии;
   - `avinashhm/welding-defect-yolov8-full-training` — детекция трещин.
2. Написать конвертер вывода YOLO:
   - маски сегментации → `polygon` из нормализованных `[x, y]`;
   - боксы → `bbox` `[x_min, y_min, x_max, y_max]`;
   - координаты восстановить относительно исходного изображения после
     resize/letterbox, затем нормализовать по его ширине и высоте.
3. Объединить результаты двух моделей в `Defect[]` и сопоставить с узлами
   оборудования (`node_id`). Технические характеристики дефекта не
   предсказываются: frontend берёт `specs` узла из карточки оборудования.
4. Передать в LLM: имя оборудования, возраст узла, дату последнего ТО,
   список дефектов с уверенностью. Возраст узла сейчас отдельным полем в
   схеме не задан: согласовать источник, не подставлять выдуманное значение.
5. Не считать демо-классы «масляный след»/«износ крепления» доказанными
   возможностями моделей; использовать их реальные классы и согласованный
   перевод в `Defect`.

Функции-конвертеры должны быть чистыми и покрыты unit-тестами:

```python
masks_to_polygons(masks) -> list[list[tuple[float, float]]]
boxes_to_bbox(boxes, width, height) -> list[tuple[float, float, float, float]]
```

### 6.2. LLM «Главный эксперт ТОиР»

Системный промпт должен задавать роль и требовать **строгий JSON без markdown**.
Минимальная формулировка:

```text
Ты — «Главный эксперт ТОиР». Оцени переданные сведения об оборудовании,
возрасте узла, последнем ТО и найденных дефектах с уверенностью моделей.
Не выдумывай измерения, причины или паспортные характеристики. Причину
формулируй как вероятную; отсутствие данных явно отмечай в тексте.
Верни только JSON с ключами criticality, probable_cause, recommendation_steps.
criticality: одно из low, medium, high; probable_cause: непустая строка;
recommendation_steps: от 1 до 10 непустых строк. Не добавляй другие ключи.
```

Пример допустимого ответа:

```json
{
  "criticality": "high",
  "probable_cause": "Возможна усталость материала; причина требует проверки.",
  "recommendation_steps": ["Остановить агрегат.", "Провести контроль корпуса."]
}
```

Вход функции:

```text
equipment_name, node_age, last_maintenance_at, defects[]
```

Выход валидировать Pydantic, запрещая лишние ключи. В real-режиме отсутствие
ключа, недоступность сервиса или невалидный ответ должны давать понятную
ошибку `503` и запись в лог, а не необработанное исключение. Если отдельно
согласуется fallback на mock, честно отмечать `meta.llm_mode = "mock"`;
не выдавать заглушку за реальное заключение.

### 6.3. Swagger в первый день

В **первый день** реализации `GET /docs` должен открываться в будущем сервисе
и содержать Pydantic-схемы:

- описания всех полей `Field(description=..., examples=...)`;
- примеры `InspectionResult` и `Report` в `json_schema_extra`;
- корректные `multipart/form-data` для `/api/inspect` и `/api/reports`;
- JSON-схему `PATCH /api/reports/{id}/status` и переходы статусов;
- схемы `AuthAccount`, `Session`, `POST /api/auth/login`, `POST /api/users`,
  `reissue-key`, `invite` и `confirm-email`;
- коды ответов 200/201/202/204/401/403/404/409/410/422/429/503.

Это требование ТЗ: разработчики веба и мобилки копируют схемы из Swagger.

### 6.4. Режимы

```text
VISION_MODE=mock | real
LLM_MODE=mock | real
```

- `mock` — работает без torch/весов, отдаёт демо-дефекты.
- `real` — для vision загружает веса, для LLM вызывает сервис; при отсутствии
  нужных ресурсов возвращает понятную `503`, а не падает. Режимы независимы.
- URL, ключи и пути к весам настраиваются только на сервере, не через `VITE_*`.

### Безопасность

См. [`SECURITY.md`](SECURITY.md). Кратко:

- сессия в `sessionStorage` и `RoleGuard` — демо-ограничение UI,
  **не авторизация**;
- ключ директора и демо-ключи сотрудников из README — публичные ключи стенда;
  PBKDF2-хеширование защищает от случайного раскрытия в таблице, но не
  заменяет серверную проверку;
- открытые ключи не хранятся в справочнике `promscan:employees:v2` и в сессии;
  в демо они попадают только в mock-outbox `promscan:mail-outbox:v1`, который
  имитирует почту сотрудника и не читается интерфейсом администратора;
- mock-outbox — демонстрационная заглушка: в production письмо отправляет
  сервер, а открытый ключ не сохраняется на клиенте;
- загрузка ограничена на клиенте 10 МБ и `image/*`, серверная валидация
  сигнатуры, размера и поддерживаемых форматов всё равно обязательна;
- в mock-режиме снимки не отправляются; с `VITE_USE_MOCK_API=false`
  видеокадры/загруженные файлы уходят на API — учитывать согласие и хранение;
- в будущем нужны серверная сессия/RBAC, Argon2id, HTTPS, CSRF-защита,
  CORS allowlist, rate limiting входа/выдачи ключей и безопасная работа с
  объектным хранилищем.

`SECURITY.md` — отдельный обзор состояния демо на дату проверки, не гарантия
безопасности будущего API. Его утверждения об отсутствии сетевой отправки
относятся только к mock-режиму. Публичный демо-ключ директора находится в
README, поэтому считать его секретом нельзя.

## 11. Известные ограничения

- Backend отсутствует; endpoint'ы и Swagger описаны как будущий контракт.
- Реальные веса YOLO и LLM не подключены; требования к ресурсам, доступу
  к моделям и ключам нужно проверить при серверной реализации.
- Постоянного серверного хранилища нет. Mock-задачи и сотрудники живут в
  `localStorage`, сессия — в `sessionStorage`; после подключения backend
  источником истины станет сервер.
- Нет загрузки фото акта в объектное хранилище.
- Нет WebSocket: live-режим — таймер 1,8 с с пропуском занятых тиков.
- `Defects` и `Scanner` используют API-слой; выбор оборудования в сканере
  пока фиксирован, а real-режим автообновления списка требует polling/WebSocket.
- Авторизация и сотрудники — демо, не production: ключ проверяется в браузере,
  сессия не подписана, письма не отправляются.
- Демо-ключи находятся в README, а PBKDF2 в браузере — только заготовка;
  production требует Argon2id, HTTPS, rate limiting и серверную сессию.

## 12. Что не делать

- Не коммитить и не пушить без явной команды.
- Не писать backend в этом репозитории без отдельной задачи и не
  восстанавливать удалённый серверный прототип по собственной инициативе.
- Не менять `docs/API_CONTRACT.md` без синхронизации TypeScript-типов и,
  когда появится сервер, его схем.
- Не добавлять mock-данные в компоненты — только в `src/lib/inspection.ts`.
- Не вызывать `fetch` из компонентов — только через `src/lib/api.ts`.
- Не включать `VISION_MODE=real` без весов и проверки bbox/polygon.
- Не хранить ключи LLM/S3, реальные пароли и токены в репозитории или `VITE_*`.
- Не считать сессию из `sessionStorage` или PBKDF2-проверку в браузере
  серверным доступом и не выдавать mock за реальный инференс при ошибках API.
